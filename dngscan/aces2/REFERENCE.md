# ACES 2-derived reference kernel

This directory contains a NumPy port of the ACES 2 output transform used for
dngscan HDR rendition validation. It is **ACES 2-derived**, not claimed as a
strict bit-identical ACES 2 implementation until CTL-runtime cross-check vectors
exist.

## Source identity

The current NumPy port was originally transcribed from the 2024 development
snapshot below. The 2025 umbrella release is the conformance target, not a claim
about the current code. Its output-transform implementation changed
substantially after the development snapshot, so release conformance requires a
separate source sync plus external CTL vectors.

| Role | Repository / ref | SHA |
|------|------------------|-----|
| implementation baseline | aces-core `v2-dev-release-2` | `eeac1e140e6f04ef60b0318630ff637e5f5d60d3` |
| conformance target | aces `v2.0.0+2025.04.04` | `35e1e6ac2c26ec75433547d5d0a3a881f39bd9f5` |

The formal release pins these submodules:

| Repository | SHA |

## Public API

```python
from dngscan.aces2 import render_aces2_hdr_p3_linear

p3 = render_aces2_hdr_p3_linear(scene_rec2020_d65, capacity_ev=3.0, reference_white_nits=100.0)
```

Pipeline:

```text
Rec.2020 D65 → AP0 (Bradford CAT)
→ aces_to_JMh → tonemap_and_compress_fwd → gamut_map_fwd
→ JMh_to_XYZ → neutral-axis peak fit → Display P3 linear / reference_white_nits
```

## Input stimuli

Reusable float64 scene inputs and display-capacity parameters are stored under
`tests/aces2_vectors/`. Regenerate with:

```bash
.venv/bin/python tools/regen_aces2_vectors.py
```

These files deliberately contain **no expected output**: comparing the renderer
with output generated by the same renderer is circular. The test suite checks
float32/float64 agreement and independent transform properties. Fixed published
matrix values live in separate tests.

## Test thresholds (initial)

| Property | Threshold |
|----------|-----------|
| neutral relative error | ≤ 2e-5 |
| finite RGB absolute error (f32 vs f64) | ≤ 5e-5 |
| hue error where M ≠ 0 | ≤ 0.05° |

## Known gaps

- No `ctlrender`-generated end-to-end vectors yet. Until they exist, this port is
  ACES 2-derived and cannot claim bit-identical CTL conformance.
- Table building at import/render time is slow (~seconds per peak); cached per peak nits.
- Inverse transform not implemented (forward-only for HDR rendition).
- Chroma `REACH_GAMUT_TABLE` uses AP1 cusp M via `make_gamut_table(AP1)` per CTL
  `chromaCompression` (`cuspFromTable(h, REACH_GAMUT_TABLE)[1]`).
